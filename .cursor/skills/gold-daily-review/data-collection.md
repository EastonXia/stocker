# 黄金每日复盘 — 数据抓取清单与容错逻辑

> 本文件是 `SKILL.md` 的配套执行手册。本 skill 在 **Claude Code / Cursor CLI** 中运行,所有行情、资金、消息数据都需要通过 `WebFetch` / `WebSearch` 自行抓取,本文是这一抓取流程的标准操作手册。
>
> 设计思路与 `a-stock-closing-review/data-collection.md` 同源(Phase 0 JSON API 优先 + 跨日陷阱判断 + A/B/C 档位降级),但数据源、字段、特殊坑均针对黄金市场重新梳理。

---

## 何时使用本流程

**本流程是默认流程**:用户每次触发黄金每日复盘 skill,都按本文执行。

适用条件:
- 在 Claude Code / Cursor CLI 中调用 skill(WebFetch / WebSearch 可用)
- 复盘对象是当日已收盘的 SGE 日盘 + 当日亚欧早盘国际金
- 数据抓取覆盖率无需 100%,**宁可缺、不可编**

---

## 最佳触发时间(北京时间)

- **16:00 - 19:30 [推荐]**:SGE 日盘 15:30 已收,数据已稳定;夜盘 20:00 还未开,实时接口此时拿到的就是日盘收盘数据,**最干净**
- **20:00 之后**:**警告!黄金夜盘已开,实时接口会立即返回夜盘开盘价 / 最新价,不再是日盘收盘** —— 必须切历史日线接口拿日盘数据(详见"起手判断")
- **次日 8:00 前**:夜盘 02:30 已收,但凌晨数据可能还未稳定入库,建议 8:00 后跑(或继续走历史接口)
- **当日 15:30 前**:禁用本流程,日盘还在交易中,不符合"日盘复盘"定义

---

## 起手判断(关键!黄金特有的夜盘陷阱)

> **黄金 ≠ A 股**。A 股闭市后几乎无活动,实时接口跨日才会失真。**黄金有夜盘 20:00 - 次日 02:30,实时接口在 20:00 后立刻拿到夜盘行情** —— 这是黄金最危险的失败模式:接口不报错、数据结构正常,只是把"日盘收盘价"换成了"夜盘最新价"。

**每次执行前必做**:对比"复盘目标交易日 + 时段(日盘)" vs "当前北京时间",决定走哪条路。

| 当前时点 | 距日盘收盘 | 实时接口能否拿到日盘收盘? | 推荐路径 |
|---------|-----------|--------------------------|---------|
| 当日 15:30 - 19:59 | 0 - 4.5 小时,夜盘未开 | ✅ 能,且就是收盘价 | **走 Phase 0 实时接口** |
| 当日 20:00 - 24:00 | 夜盘已开 | ❌ 拿到的是夜盘最新价 | **走 0.8 历史日线接口** |
| 次日 0:00 - 02:30 | 夜盘进行中 | ❌ | **走 0.8 历史日线接口** |
| 次日 02:30 之后 | 夜盘已收 | ⚠️ 实时接口拿"上一笔成交价"≈ 夜盘收盘 ≠ 日盘收盘 | **走 0.8 历史日线接口** |
| 周末 / 节假日 | SGE 完全休市 | 实时接口拿到上一交易日数据,可能是日盘也可能是夜盘 | **走 0.8 历史日线接口** |

**漏判这一步 → 拿到错数据但 skill 误以为正确**(对应 `a-stock-closing-review/data-collection.md` 的"已知坑 #10"在黄金市场的强化版本)。

## Phase 0:JSON API 优先抓取(首选)

### 0.1 上海金 Au99.99 / Au(T+D)

**主源候选 1:东方财富 push2 行情**

```
# 候选 secid(首跑必须探测验证):
# Au99.99: 47.AU99_99 或 47.Au9999
# Au(T+D): 47.AUTD 或 47.Au_T_D
https://push2.eastmoney.com/api/qt/ulist.np/get?fltt=2&secids=<候选secid列表逗号分隔>&fields=f2,f3,f4,f5,f6,f12,f13,f14,f17,f18,f37
```

字段含义:
- `f2` 最新价 / `f3` 涨跌幅(%) / `f4` 涨跌额
- `f5` 成交量 / `f6` 成交额
- `f12` 代码 / `f14` 名称
- `f17` 开盘价 / `f18` 昨收价
- `f37` 持仓量(部分品种,Au(T+D) 应有)

**主源候选 2:新浪财经贵金属接口(纯文本,无需鉴权)**

```
https://hq.sinajs.cn/list=gds_AUTD,gds_AU99_99,gds_AU100g
```

返回每行 `var hq_str_xxx="..."` 格式,按 `,` 分割。**字段顺序需首跑 verify**(新浪历史上调过字段)。

注:新浪某些接口对 `Referer` 有校验,WebFetch 出现空字符串时,改抓 `https://finance.sina.com.cn/futuremarket/spotgold.shtml` 之类页面再正则提取(走 Phase 1/2)。

**首跑 secid / 字段探测协议(关键!)**:

1. 先用上方候选 URL 各跑一次 WebFetch,prompt 显式要求"原样返回 JSON / 文本,不解读"
2. 拿到响应后,人工核对:
   - 价格量级是否合理(Au99.99 应在 600 - 900 元/克区间,2026 年初约 700 - 800)
   - Au(T+D) 价格应略偏离 Au99.99(差额 ±2 元/克内)
3. 候选都不可用时,降级 Phase 1(WebSearch + 财经文章页)
4. **首次成功验证后,把可用 URL 和字段映射回写到本文件"已验证 secid / 数据源"段**(末尾迭代记录里同步)

### 0.2 SHFE 沪金期货主力(参考辅助)

主力合约代码格式:`AU<年月>`,例 `AU2406`(2024 年 6 月合约)。每年初 / 期约滚动一次,具体当期主力以"成交量最大"为准。

```
# 候选 secid:113.au<年月> 或 113.AU<年月>
https://push2.eastmoney.com/api/qt/ulist.np/get?fltt=2&secids=113.<主力代码>&fields=f2,f3,f4,f5,f6,f12,f14,f17,f18,f37
```

主力合约判定:可先跑期货板块榜(`fs=m:113+t:1`)按成交量降序找 TOP 1。

https://push2.eastmoney.com/api/qt/ulist.np/get?fltt=2&secids=<候选>&fields=f2,f3,f4,f12,f14

### 0.5 黄金 ETF(518880 / 159934 / 518680)

```
https://push2.eastmoney.com/api/qt/ulist.np/get?fltt=2&secids=1.518880,0.159934,1.518680&fields=f2,f3,f4,f5,f6,f8,f12,f14,f15,f16,f17,f18
```

字段:
- `f2` 最新价 / `f3` 涨跌幅 / `f5` 成交量 / `f6` 成交额
- `f8` 换手率 / `f15` 最高 / `f16` 最低 / `f17` 开盘 / `f18` 昨收

**ETF 净申购份额** 不在以上接口中,需要走以下任一路径:
- 东财基金详情页(`https://fundf10.eastmoney.com/jbgk_<代码>.html`),抓"基金份额"日度变化(动态页,可能拿不到)
- WebSearch `518880 净申购 净赎回 YYYY年M月D日`,从财经新闻摘取

### 0.6 SGE 上海金基准价(上下午)

- **官方源**:上海黄金交易所官网 `https://www.sge.com.cn/` 行情公告页(每日 10:15 / 14:15 后发布上下午定盘价)
- **WebFetch 注意**:页面动态,可能拿不到当日;改用 WebSearch `上海金基准价 YYYY年M月D日 上午 下午`

### 0.7 SPDR GLD 黄金 ETF 持仓(可选,日度更新)

- **官方源**:`https://www.spdrgoldshares.com/`(英文页,持仓吨数日度更新,T+1 滞后)
- 中文摘录源:WebSearch `SPDR 黄金ETF 持仓 YYYY年M月D日`

### 0.8 push2his 历史日线接口(跨日 / 周末 / 20:00 后复盘必用)

> 起手判断决定要走这个接口时,**Phase 0 上述实时接口全部禁用**(避免双数据混淆模型)。

**接口 URL**:
```
https://push2his.eastmoney.com/api/qt/stock/kline/get?secid=<secid>&klt=101&fqt=0&beg=YYYYMMDD&end=YYYYMMDD&fields1=f1,f3&fields2=f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61
```

**适用范围**:Phase 0 中所有有 secid 的标的(Au99.99、Au(T+D)、SHFE 沪金、ETF、伦敦金、COMEX、DXY)都可以查日 K 线。

**返回**(`data.klines` 每行逗号分隔字符串):
```
日期, 开盘, 收盘, 最高, 最低, 成交量, 成交额, 振幅(%), 涨跌幅(%), 涨跌额, 换手率(%)
```

**参数**:
- `secid` 同实时接口
- `klt=101` 日 K
- `fqt=0` 不复权
- `beg` / `end` 目标交易日 8 位数字(同日两端相等,例 `20260508`)

### WebFetch 调 JSON API 的 prompt 模板

调 JSON 接口必须显式禁止总结、要求保留原始数值:

```
该 URL 返回 JSON 格式数据。处理要求:
1. 不要总结、不要转译、不要润色
2. 提取 data.diff 数组中每项的字段:f2、f3、f12、f14、f37(若有)
3. 每行格式:"代码=f12 | 名称=f14 | 最新价=f2 | 涨跌幅=f3% | 持仓量=f37"
4. 如果 JSON 解析失败或返回空数组,直接说"接口返回空"
```

调新浪文本接口的模板:

```
该 URL 返回类似 var hq_str_xxx="字段1,字段2,..." 的多行文本。处理要求:
1. 原样返回每一行(去掉 var 前缀和分号),不要解读
2. 如果某行是 var hq_str_xxx="" 空字符串,标"接口返回空"
```

### Phase 0 数据校验

- **价格量级**:Au99.99 / Au(T+D) 应在 600 - 900 元/克(2026 年区间);伦敦金 1500 - 3000 美元/盎司;DXY 90 - 115;COMEX 与伦敦金现货差额通常 ±5 美元
- **时间戳匹配**:接口若有时间字段,确认是目标交易日(警惕"看似返回但日期错位")
- **多接口交叉**:Au(T+D) 折美元价 vs 伦敦金,价差应在 ±20 美元/盎司内,超出视为某一边数据有误

### Phase 0 失败时的处理

- **单接口失败**:等 3 - 5 秒重试 1 次,仍失败切备源
- **secid 候选全部不通**:报告中标"未获取到 XX",在 Phase 1 做补救
- **全部主源 + 备源失败**:走 Phase 1 WebSearch,报告必须标明"Phase 0 全失败,数据来自二手综述,精度下降"

### Phase 1:并行 WebSearch(找当天具体报道)

并行发起 3 - 5 个搜索:

| 目的 | 推荐 query 模板 |
|------|----------------|
| 上海金日盘收盘 | `YYYY年M月D日 上海金 Au99.99 Au(T+D) 收盘` |

## 已知坑(踩过的 / 推断的,别再踩)

> 黄金 skill 首次发布时,部分坑由 a-stock-closing-review 经验类推 + 黄金市场结构推断而来,首跑后须根据实测情况补充 / 修正。

1. **黄金夜盘陷阱(最危险!)**:北京 20:00 之后跑日盘复盘,实时接口立刻返回夜盘开盘价 / 最新价,接口不报错、结构正常 —— 必须在起手判断阶段切历史日线接口。这是黄金独有的最危险陷阱。
2. **secid 候选不一定准**:东财对 SGE / 外汇贵金属代码的内部 secid 命名有变化历史,首跑必须按"探测协议"验证,验证通过的 secid 回写到本文件末尾的"已验证 secid / 数据源"表。
3. **新浪 hq 接口字段顺序**:历史上新浪调过字段顺序,具体含义以"首跑探测确认"为准,不要把 a-stock 复盘里的字段映射直接套过来。
4. **JS 动态行情页 WebFetch 必空**:东财黄金行情页(`http://quote.eastmoney.com/sj/...`)、同花顺贵金属 fupan 页、新浪黄金行情页都依赖 JS 渲染,WebFetch 静态抓取拿到全是骨架,**只能走 Phase 0 JSON API**。
5. **跨日陷阱(同 a-stock #10 但更激进)**:黄金市场近全时段活跃,跨日运行实时接口的失真比 A 股更立竿见影 —— 哪怕 02:30 夜盘收盘后跑,实时接口"上一笔成交价"也是夜盘收盘价不是日盘收盘价,必须走历史日线接口。
6. **基准价 vs 收盘价口径**:SGE 上午基准价(10:15)是"集中竞价基准",和 Au99.99 当日 9:00 开盘价、午盘 10:15 瞬时价、当日收盘价是 4 个不同概念,不要混用。
7. **Au(T+D) 与 Au99.99 不能简单等同**:T+D 是延期合约带杠杆,有持仓量、有保证金、有夜盘;Au99.99 是即时现货。两者价格短期可有 ±2 元/克偏离,这本身就是分析素材,不是数据错误。
8. **国际金时区错位**:伦敦金 / COMEX 走的是 UTC 或纽约时区,我们看的"今日 5 月 8 日伦敦金收盘"通常对应北京 5 月 9 日凌晨 —— **16:00 跑只能看到当日亚盘 + 欧盘开盘约 1 小时数据,不是欧美主交易段** —— 报告必须明示这点。
9. **AI 摘要日期混淆**:同 a-stock 经验,WebSearch 结果中的 AI 摘要可能把上一交易日数据回填到当日。任何 P0 字段从 Phase 1 拿到时,必须和 Phase 0 JSON 交叉对比;拿不到 Phase 0 时,把同一字段从至少 2 篇独立文章页各取一遍,数值一致才采信。
10. **新浪 hq 接口的 Referer 校验**:新浪某些子接口对 `Referer` 有校验,WebFetch 默认无 Referer 时可能返回空字符串或 HTTP 403。空响应 / 403 不一定是数据缺失,可能是接口拒答 —— 此时改走文章页路径。**2026-05-09 实测**:`https://hq.sinajs.cn/list=gds_AU99_99,gds_AUTD,hf_XAU,hf_GC` 直接返回 403 Forbidden,确认 Referer 校验生效,新浪 hq 路径在 WebFetch 环境下不可用。

## 数据冲突与校验

多源对同一字段给出不同数据时,按以下优先级采信:

1. **官方 / 原始源优先**:上金所官网 > 新浪 hq 接口 > 东财 push2 > 财经文章页 > AI 摘要
2. **时间晚的优先**:16:00 后文章 > 14:00 文章 > 午盘文章
3. **精度高的优先**:带小数点(728.42 元/克)> 模糊表述("约 728 元/克")

**强制校验项**(抓完 P0 数据后,产出前逐条检查):

- [ ] Au(T+D) 折美元价 vs 伦敦金现货,差额绝对值 ≤ 20 美元/盎司(超出视为汇率 / 数据问题)
- [ ] Au99.99 与 Au(T+D) 收盘差额 |x| ≤ 5 元/克(超出视为某一边接口异常)
- [ ] 沪金期货主力价格(元/克)与 Au(T+D) 价格大致接近(偏离 < 5 元/克)
- [ ] 国际金涨跌方向与上海金涨跌方向不应剧烈背离(背离时检查汇率是否同步剧烈波动)
- [ ] 消息面日期与复盘日期一致(避免把前一日政策当今日催化)

任一项失败 → 标"数据存疑,以 XXX 源为准",不强行消弭矛盾。

## 容错降级规则

按数据完整度分三档输出:

### 档位 A:P0 字段齐全(Au99.99 + Au(T+D) + 伦敦金 + DXY)

正常按 SKILL.md 10 段输出,数据缺失项逐条标"未获取",**不降级**。

### 档位 B:P0 缺 1 - 2 项(例如缺 DXY 或缺 Au(T+D) 持仓量)

- 报告开头加一行:"本次复盘因缺失 XX 数据,完整性受限,请结合其他来源参考"
- 缺失字段涉及的段落(如美元因子、持仓变化),**只做定性分析,不做定量判断**
- 6 因子诊断段中,缺失数据的因子标"未获取 / 中性",不强行打分
- 预测部分的"依据"必须避开缺失字段

### 档位 C:P0 缺 3 项及以上

- **不输出完整复盘报告,不归档** —— 改为向用户说明:"公开源今日数据覆盖不足,无法完成合格复盘。可能原因:数据源限流 / 网络阻断 / 当日为非交易日(节假日 SGE 休市)。建议稍后重试或手动贴入数据。"
- 附上已抓到的片段信息作为参考,但明确标注为"片段信息,不构成复盘"
- 避免硬写一份"看起来像但内容靠猜"的报告

## 禁止行为(违反即整份报告作废)

1. **禁止凭记忆补全数据**。"印象中昨天伦敦金 2350" 也不行,只要今日数据源没给出,标"未获取"。
2. **禁止把昨日数据当今日数据**。搜索结果常混入前一日数据,确认日期是强制动作。
3. **禁止用"约""大约""估计"美化缺失**。要么有数据,要么没数据。
4. **禁止把夜盘数据写成日盘数据**。20:00 后跑、未切历史接口的实时数据,绝不能放在"日盘收盘"位置。
5. **禁止把欧美主交易段数据冒充已发生**。16:00 跑只能看到欧盘开盘约 1 小时,后续走势不能预先编写。
6. **禁止把定性描述当定量数据**。"沪金走强" ≠ "Au(T+D) +1.2%",前者不能出现在涨幅数值位。

## 抓取效率建议

一次完整抓取预算:**Phase 0 ≤ 8 次 WebFetch + Phase 2 ≤ 4 次 WebSearch + 3 次 WebFetch**(并行执行,总耗时约 30 - 90 秒)。超过这个量级说明数据源失效,应换策略而非盲目加次数。

**执行顺序**:
1. **起手判断**(目标日 vs 当前北京时间,决定走实时还是历史接口)
2. **Phase 0**:并行发 6 - 8 次 WebFetch 调 JSON API(按 0.1 - 0.7 顺序;需历史时切到 0.8)
3. 校验 Phase 0 数据(数值合理性、时间戳、跨接口自洽)
4. **Phase 0 拿到 P0 字段** → 跳过 Phase 1,直接进入 Phase 2 抓消息面 + 缺失的 P1/P2 字段(并行 3 - 4 次 WebSearch)
5. **Phase 0 P0 字段缺失** → 才回退到 Phase 1 WebSearch + Phase 2 WebFetch 文章页
6. 终止抓取,进入写作
